This page shows a full gdhealth run on [**godot-open-rpg**](https://github.com/gdquest-demos/godot-open-rpg), a real open-source RPG tutorial project by [GDQuest](https://www.gdquest.com/) targeting Godot 4.6.2.

The project has **78 GDScript files**, **5 341 SLOC**, across 4 logical layers (combat, field, common, overworld).

```sh
git clone https://github.com/gdquest-demos/godot-open-rpg
cd godot-open-rpg
# add gdhealth.toml (see Configuration tab below)
gdhealth health --root .
```

## Browser viewer (`emerge-html`)

Run to generate the interactive graph:

```sh
gdhealth graph --root . --format emerge-html
open reports/code-health/browser/emerge.html
```

**File dependencies — community coloring.** Each color is a Louvain cluster. The 61 clusters and sparse edges reflect GDQuest's deliberately loosely coupled tutorial architecture:

![File dependency graph, community coloring](/showcase/emerge-community.png)

**Hotspot coloring.** Green = low complexity, amber/red = high hotspot score. The few warm nodes — `player_controller.gd`, `pathfinder.gd`, `ui_battler_target_cursor.gd` — are exactly the files handling the most input branching and pathfinding logic:

![File dependency graph, hotspot coloring](/showcase/emerge-hotspot.png)

**Entity dependencies graph.** Switching to entity-level view shows only 4 cross-entity edges, confirming the codebase uses composition over inheritance:

![Entity dependency graph](/showcase/emerge-entity-deps.png)

**Node click — `treasure_chest_interaction.gd`.** The SELECTION panel shows per-file metrics inline: 36 lines, fan-in 0, fan-out 1, 1 function, complexity 3, hotspot 17:

![Node selected in the graph](/showcase/emerge-node-click.png)

## What the results tell us

This is a well-structured tutorial codebase. The key signals:

| Signal | Value | Interpretation |
|---|---|---|
| Cycles | 0 | Clean dependency graph, no circular coupling |
| Critical findings | 0 | No severe threshold violations |
| Warning findings | 11 | All in combat input handlers and pathfinding — expected complexity |
| Communities | 61 out of 78 files | Extremely loose coupling; most files stand alone |
| Top hotspot | `player_controller.gd` (131) | Input handling is the most complex concern, reasonable for a game |
| Top function | `_unhandled_input` (cyclomatic 14) | Input branching concentrated in one function — refactor candidate |

Running `gdhealth health --root . --fail-on critical` on this project exits **0** — it passes CI out of the box.
